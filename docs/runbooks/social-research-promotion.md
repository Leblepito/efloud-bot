# Social-Research Promotion Runbook

This runbook governs how a hypothesis generated by the social-learning pipeline
(`backend/social/*`, `scripts/research_social_strategy.py`) is allowed to influence
**live trading behaviour**. The default state of every social-derived hypothesis
is `research_only`. Promotion to live is a deliberate, gated, human-approved
event.

## Scope

Applies to anything that:

- Originates from `state/social_doctrine.jsonl` or other archived public content.
- Is materialised as a `configs/candidates/candidate_*.yaml`.
- Touches engine confluence weights, SMC v2 toggles, lifecycle thresholds, or
  any field that the live runtime reads from `configs/config.phase2_1k.yaml`.

It does **not** apply to:

- Bugfixes in `engine/`, `exchange/`, or `backend/` that are not driven by a
  social hypothesis.
- Pure observability or dashboard work.
- Doc-only changes.

## Roles

| Role | Responsibility |
|------|----------------|
| Architect (Opus / Claude Code) | Writes spec, code review, runs gates 1–4 locally, prepares promotion PR draft. |
| Hermes / Utku | Sole authority for gates 5–7 (shadow activation, config edits, deploy, rollback). |
| Reviewer agent | `efloud-risk-ops-reviewer` is mandatory for any PR that touches risk/safety surfaces. |

The architect never edits `configs/config.phase2_1k.yaml`, `.env`, or
`docker-compose.prod.yml` as part of promotion. Those are Hermes-only edits.

## Promotion gates

A hypothesis may be promoted only when **all** gates below have passed in
order. Skipping a gate is not allowed.

### Gate 1 — Code & test hygiene

- All target tests green:
  ```bash
  pytest backend/tests/test_social_feeds.py \
         backend/tests/test_social_doctrine.py \
         backend/tests/test_social_archive.py \
         backend/tests/test_social_hypotheses.py \
         backend/tests/test_social_reports.py \
         backend/tests/test_backtest_social_tags.py -q
  ```
- No new lint/type regressions in touched modules.
- Candidate config is generated by `scripts/research_social_strategy.py` and
  written **only** under `configs/candidates/`. The script must never write
  to any production-control file. As defense-in-depth, the script's write
  paths are validated against `PROTECTED_OUTPUT_NAMES` (currently:
  `config.yaml`, `config.phase2_1k.yaml`, `docker-compose.prod.yml`, `.env`);
  any attempt to coerce the candidate output path to one of these names
  raises before the file is opened. The runbook list and the code list are
  pinned together by `backend/tests/test_research_script_output_guard.py`
  (`test_protected_set_includes_production_control_files`) — when adding a
  new production-control file, update both sides and that test.

### Gate 2 — 180-day backtest compare

- Run:
  ```bash
  python -m backtest.cli compare \
    --symbols BTC/USDT,ETH/USDT,SOL/USDT \
    --period-days 180 \
    --config configs/config.phase2_1k.yaml \
    --hypothesis <hypothesis_id>
  ```
- Report must be archived under `reports/social_research/<date>_<hypothesis>/`.
- The report **must not** contain `hard_reject` in `gates`.
- The hypothesis ID and `doctrine_tags` must be present in the report JSON
  (locked by `backend/tests/test_backtest_social_tags.py`).

### Gate 3 — Risk envelope

Compared to the latest baseline run on the same symbols and period:

| Metric | Rule |
|--------|------|
| `max_drawdown_pct` | ≤ baseline + 10 percentage points (absolute, not relative — e.g., baseline 12 % → cap 22 %). |
| `stop_hunt_rate` | Equal or better. A worsening stop-hunt rate is an automatic reject. |
| `avg_realized_rr` | Not worse than baseline by more than 10%. |
| `win_rate` | Informational only — not a hard gate. |

If any of the hard rules fail, the hypothesis stays at `research_only` and the
PR is closed with a link to the failing report.

### Gate 4 — Doctrine-to-engine gap

- Run `python -m scripts.report_doctrine_engine_gap` and inspect
  `reports/social_research/latest_gap_report.md`.
- Any new concept introduced by the hypothesis must already be implemented in
  `engine/smc_v2/*` or be explicitly flagged as inert (`enabled: false`) in the
  candidate config. Promotion of a hypothesis that depends on an unimplemented
  concept is forbidden.

### Gate 5 — v2 shadow observation (Hermes-only)

- Hypothesis must run in v2 shadow mode for **at least 7 calendar days** on the
  live data feed without producing any live order.
- Shadow log must contain at least 3 would-have-been signals per active symbol
  or at least 10 in total over the 7-day window. Hermes raises the floor if
  the shadow window is shorter than expected or if signal frequency is below
  the v1 baseline for the same period.
- Shadow run must not raise unexpected errors in the bot log.
- Hermes confirms shadow health from the dashboard and Telegram alerter feed.

### Gate 6 — Human approval (Hermes-only)

- Hermes and Utku sign off on the promotion PR.
- Sign-off message must reference: hypothesis ID, backtest report path, shadow
  log range, and the exact diff against `configs/config.phase2_1k.yaml`.
- Sign-off is required even if all earlier gates are green.

### Gate 7 — Controlled rollout (Hermes-only)

- The promotion edit is applied **only** to `configs/config.phase2_1k.yaml`
  (or the active production config), never to a candidate file.
- Initial rollout is half-size: `risk_per_trade_pct` for the affected setup is
  halved for the first 7 days post-merge.
- Deploy via the standard compose recreate step (`docker compose -f
  docker-compose.prod.yml up -d`); plain `docker restart` is forbidden after
  env or compose changes.
- Migrations, if any, are executed manually by Hermes per CLAUDE.md §5.

## Rollback

- If any post-promotion metric breaches the Gate 3 envelope within the first
  7 days, Hermes reverts `configs/config.phase2_1k.yaml` to the
  pre-promotion commit and redeploys via compose recreate.
- The rollback commit must reference the hypothesis ID and the breached
  metric.
- The hypothesis returns to `research_only`; the candidate config under
  `configs/candidates/` is kept for forensic re-runs.
- Hermes marks the originating hypothesis back to `research_only` in the
  hypothesis store (`state/social_doctrine.jsonl` annotations or the
  hypotheses registry consumed by `backend/social/reports.py`) so the same
  ID cannot be auto-re-promoted by a later research run.

## Records

For every promotion attempt (passed or failed) the following artefacts must
exist before the PR is merged:

- `configs/candidates/candidate_<hypothesis_id>.yaml`
- `reports/social_research/<date>_<hypothesis>/compare_report.json`
- `reports/social_research/latest_gap_report.md` (snapshot at decision time)
- PR description listing each gate with PASS / WARN / REJECT and a link to the
  evidence file.

## Forbidden shortcuts

- ❌ Promoting straight from `configs/candidates/` to live without compare +
  shadow.
- ❌ Letting an LLM or social parser write the final live config.
- ❌ Editing `config.yaml` or `config.phase2_1k.yaml` from a research script.
- ❌ Symlinking, copying or renaming a `configs/candidates/*.yaml` over
  `configs/config.phase2_1k.yaml` (or any active production config) without
  going through Gate 7. The Gate 7 edit must be a hand-written diff against
  the live config, never a file replacement.
- ❌ Bypassing Gate 5 by running shadow mode with `dry_run: true`, a
  `--paper`/`--no-orders` flag, or any path that suppresses both real orders
  *and* would-have-been signal logging. Gate 5 requires real signal emission
  with order placement disabled at the exchange layer only.
- ❌ Bumping the half-size `risk_per_trade_pct` cap defined in Gate 7 within
  the first 7 days of rollout. Cap changes during the rollout window require
  a fresh Gate 6 sign-off.
- ❌ Skipping the 7-day shadow window because "the backtest looked good".
- ❌ Merging a promotion PR without `efloud-risk-ops-reviewer` sign-off.
